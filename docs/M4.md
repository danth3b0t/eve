# M4 — onboarding and diagnostics

**Status: guided Convex onboarding/incremental update, plan/list/doctor diagnostics and typed create review.** Backends, consumers and listeners are separate discovery paths. A non-TTY cannot receive interactive approval; automation uses `--yes` or JSON without prompts.

## Plan boundary

- `eve plan <branch> [--from]` uses the canonical committed manifest, never source working-copy overrides. It runs the same bounded Git, raw-file/tracking/ignore and lexical path preflight used by create and returns branch, source, target commit, manifest hash, prospective destinations and declared resource/service structures.
- Portblocks, allocations, workspace UUIDs, worktrees, remote references, HMAC keys, credentials and provider objects are all intentionally absent. A successful plan only means the committed inputs passed read-only evaluation; it does not prove loader behavior, port availability, provider permission or permission to mutate.
- The command does not initialize/open EVE's protected registry, launch the project, fetch provider state or display private file contents. Structural reports include declared env key names and paths, never local deployment keys or unmanaged values.
- An interactive `eve create` contacts that same preview first, and typed `yes` alone moves into durable intent. Stderr contains no env values or secrets, cancellation wins, and an empty answer, offline input or non-TTY refuses without mutation. State opening and source registration wait until approval.


## Init boundary

- `init --convex` identifies committed `convex.json` packages and allows a Convex-only manifest without requiring Vite, Next.js, or a listener. Multiple backends are rejected unless `--backend-path` selects exactly one discovered candidate.
- Services are still small and conservative: ordinary `vite` scripts with `vite.config.js` or `vite.config.ts`. Only configs proving `loadEnv`, `strictPort` and `PORT` receive a native EVE port claim. Other recognized services may bind provider outputs but report listener support unresolved rather than inventing a port.
- Committed evidence discovers conventional public Convex keys. Existing approved `.env.local` destinations add URL relationships by key name, including custom keys only when the selected backend's own destination contains a matching public `CONVEX_URL`/`CONVEX_SITE_URL` hint. Source/dotenv values, stale deployment selectors and secrets never enter the proposal, manifest or logs.
- Convex development defaults are the backend defaults/secrets baseline. Empty remote overrides skip remote env list/update. A reviewed `--site-url-service` is the only ordinary onboarding declaration that updates remote state, and it points only that new deployment to its generated service URL.
- `--write --yes` creates `eve.toml` exclusively with `0600`; `--update --write --yes` replaces it through a synced private temporary after preserving the committed manifest. No code/scripts/ignore files, state, credentials, provider resources or commits are produced. Updates reuse committed project/profile bindings unless explicitly replaced.
## Interpolation inventory

- `eve keys [--json]` reports only the exact interpolation variables supported by the current committed manifest: workspace identity/branch/port base, service ports/URLs and Convex public outputs. It performs no EVE state opening, provider request, cloud environment read or destination dotenv read.
- `eve keys` is the reference an editor, LLM agent, or custom configuration author should run before writing `eve.toml`; init/write still remains the preferred source for generated bindings.

## CLI transparency
- Cobra is the single command, help, completion and parsing grammar. Flags are parsed once by registered command definitions; business handlers receive typed options rather than reconstructing argv. Help is derived from actual children/flags/defaults and can be requested as versioned JSON through `eve help <path> --json`.
- Bare informational groups—including `eve`, `eve auth`, `eve auth convex`, and `eve completion`—return scoped guidance with exit 0. Unknown commands/flags, missing operands and extra generator operands are local exit-2 usage errors and never repair requests into `--yes` or another action.
- `eve completion setup [--shell auto|bash|zsh] [--json]` prints shell-specific prerequisites, current-session/persistent setup, verification, troubleshooting and removal instructions. `$SHELL` is only a labeled hint; unsupported/malicious values yield both supported guides and never result in an automatic script mode.
- `eve completion bash` and `eve completion zsh` print only reviewed scripts. The version-pinned transport adapter invokes EVE with argument arrays rather than evaluated request strings, disables generic filename fallback on old Bash, and fails closed if the pinned Cobra template changes. Real PTY tests verify Bash/Zsh insertion and literal handling of command-substitution text.
- The Bash script includes an explicit FZF trigger bridge. Typing the trigger (`**` unless changed) sends one narrowed protocol request to the same Cobra candidate providers, feeds only sanitized insertion/description rows to fzf, and inserts the selected identity; canceled/empty selection remains inert. `EVE_FZF_COMPLETION=0` disables the bridge without changing ordinary Tab. A real fzf PTY test verifies the selection path.
- Dynamic candidates are read-only, local, bounded and command-scoped: repository workspace selectors, create targets, local heads/tags/cached remote refs, full canonical GC UUIDs, credential profile names, recorded project bindings and bounded onboarding IDs. Missing/busy/newer state, absent Git and slow metadata degrade without writable registry initialization, token-object reads, provider calls, fetches or startup-file changes.
- Command `effects` are additive versioned metadata. `create --dry-run`, `sync --dry-run`, `resume --dry-run`, and lifecycle destroy `--dry-run` present planned effects with no worktree, durable intent, journal, credential, branch, remote env, or claim changes.
- Manual raw worktree removal remains registry evidence; `gc --workspace ID` can be completed after verified absence exactly, never by filesystem scanning.
- Non-JSON `create` emits safe phase labels such as reserving allocations, creating the worktree, provisioning resources, staging files and publication to stderr. No HTTP bodies, credential material or file contents are printed; `--json` remains clean.

## List boundary

- Default scope is the explicitly registered canonical source associated with the invoking checkout (including a linked worktree). Registered metadata alone is not rechecked ownership, so create/resume/destroy still verify Git and filesystem identities independently.
- `--all` enumerates every registered repository in the user registry. Listings include only live workspaces by default and deliberately omit `destroyed` tombstones. A workspace row carries ID, branch, path, state, phase, generation, public ports/URLs and public Convex identity/expiry.
- The command opens the existing database read-only, creates no schema/lock/profile objects and performs no network, Git mutation, port release, file image creation, or provider inference. Values/selectors and deploy credentials are never emitted.
- Output remains additive-compatible JSON schema version 1; groups may gain fields but current `workspaces`, IDs, paths, states, endpoints and resources stay public metadata.
- Empty groups report `no live workspaces`; concurrency races in reads are a diagnostic, not an authorization to repair.
- `status --refresh` uses the doctor's provider identity adapter only. On non-cloud workspaces it reports `not_checked`; it does not execute env/key reads or pretend read-only evidence is runtime health.

## Doctor boundary

- Every check has one of `pass`, `warning`, `fail`, `not_checked`. The project is never launched/run, and static load checks stay `not_checked`. A listener is at most a warning, never process identity/health proof. Changing endpoints are not fixed automatically.
- Registry/Git checks verify recorded workspace state, branch/path identifiers and the current committed manifest. Updated branch revisions with file edits become warnings rather than authorization; visible Git changes block lifecycle mutations before any provider write.
- File checks compare every current managed destination's bytes and privileges against the published generation HMAC. Differences are warnings when a narrower sync may still accept them; missing/unsafe destinations are failures. Remote doctor verifies only exact project/deployment/reference/name/type/default/expiry through the management API; no environment values, deploy keys or broad project reads are used.
- JSON keeps check IDs, paths, states, expiry evidence and runtimes public. Unmanaged/untracked file contents, database rows and secret selector values are never printed.

## Evidence

- An external CLI test proves plan JSON exposes branch/target/file structure while creating no registry database or worktree.
- Init/CLI tests cover backend-only manifests, strict/TS Vite bounds, conventional and custom local URL bindings without value leaks, unmatched custom URL refusal, explicit backend/site URL selection, incremental project/profile inheritance, dry-run/write consent, atomic `0600` update, and plan after commit with no EVE state.
- A real CLI test registers a repository, creates one native workspace and verifies `list` and `list --all` JSON with the repository label, assigned service port and workspace UUID/path.
- Destroying that workspace removes it from the default read-only list. Unchanged EVE-created branch metadata is pruned exactly, while pre-existing/divergent branches and audit tombstones are preserved outside the report.
- Doctor tests pass without a running application, then report file drift and visible Git changes as warnings while runtime/loader remain `not_checked`. Contract-fake Convex remote checks match exact identity without env/key queries. CLI output is tested for pass and `not_checked` diagnostics.
- Help/completion regression tests prove bare group success, nested JSON help, scoped usage errors, structured setup, command-specific dynamic candidates, global exact-UUID GC completion, bounded state degradation, and real Bash/Zsh PTY insertion without request/candidate shell execution. Generated grammar snapshots live in [HELP_SNAPSHOTS.md](HELP_SNAPSHOTS.md).

## Not implemented

Broader framework discovery, custom remote-env cloning, interactive token entry during init, and prewarmed provider pools remain out of scope. Unresolved loader support is never converted into an endpoint claim.
