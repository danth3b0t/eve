## Scope and evidence

The fixture is two Vite frontends and a separate Convex backend. Its root script is `turbo run dev`; leaf scripts are `vite`, `vite`, and `convex dev`. Turbo remains in its default strict environment mode, with explicit existing pass-through keys and uncached persistent dev tasks. Each frontend's **baseline application config** explicitly reads `PORT` through Vite's `loadEnv` and enables `strictPort`. Vite natively supplies `VITE_CONVEX_URL` and `VITE_CONVEX_SITE_URL` to the browser module.

Tests copy the fixture into an isolated temporary Git repository and **commit it before configuring it**. Worktrees come from that commit. Dependency installation is a separate `bun install --frozen-lockfile`, never provisioning behavior. Launch PATH contains only Bun, Node, Git, and fixture dependencies; HOME is fresh, and ambient credentials/configuration are not inherited. No EVE, mise, injected dotenv wrapper, or shell activation participates.

### The rejected loading assumption

A first candidate read only `process.env.PORT` in Vite config, assuming Bun would populate it from leaf `.env.local`. A direct `bun -e` probe saw the variable, but `bun run dev` → the external `vite` executable did not; both frontend tasks attempted 5173. Root dotenv values likewise did not propagate through this graph.

That candidate is retained in [testdata/unsupported-launch/vite.config.js](../testdata/unsupported-launch/vite.config.js). It is not repaired during workspace preparation. The supported baseline is a **separate, explicitly native-loader application configuration**, established before the tests create worktrees. This does not authorize EVE to add `loadEnv`, change a script, or teach an existing app to consume `PORT`. An app like the rejected candidate must be reported unsupported. Ambient variables, hardcoded flags, alternative env-file arguments, and other Bun versions can change this outcome; don't infer arbitrary command behavior from this fixture.

Shared-root loaders, Next.js, additional listener keys, disabled autoloading/explicit `--env-file` scripts, and cached preparation tasks remain unverified layouts, not implied support.

## Reproduce local evidence

From the repository root, using the versions above:

```sh
go test ./...
go vet ./...
EVE_M0_NATIVE=1 go test -race ./tests/m0 -count=1 -v
```

`-race` requires the Go race toolchain/C compiler on supported hosts; omit it for a dependency-light probe. Tests install fixture packages into temporary checkouts and clean those checkouts up. No cloud calls occur unless the separate live flag is set. The unsupported fixture test skips explicitly if its fixed fallback port 5173 is already occupied.

## Live Convex runbook

**This test authorizes three additional nondefault cloud dev deployments and their exact cleanup.** Use a dedicated, nonproduction project with no real application data/secrets. Costs and provider quotas can apply. Do not use a production team's token just to get the test passing.

Prerequisites:

1. Existing `team:project`, an existing **cloud default dev deployment**, and a development team access token authorized for that team/project. No CLI login scraping is used.
2. In that dedicated project's **development defaults**, explicitly set the public marker `EVE_M0_DEFAULT=eve-m0-public-default`. The test never changes defaults or copies existing deployment data. Set this before creating the test deployments.
3. Entitlement for three extra deployments and the requested **five-day** expiration. Rejection fails the test; it does not clamp or remove expiry.
4. Pinned fixture runtimes, outbound Convex/package-registry access, and time for ordinary CLI code deployment. No interactive backend retargeting should be necessary.

Example in Bash, keeping the token out of argv and shell history:

```sh
read -rsp 'Development team token: ' EVE_CONVEX_TOKEN; printf '\n'
export EVE_CONVEX_TOKEN
export EVE_M0_PROJECT='your-development-team:your-m0-project'
# Optional, explicit regional probe: export EVE_M0_REGION=aws-eu-west-1
EVE_M0_LIVE=1 go test ./tests/m0 -run '^TestLiveConvexAndNativeLaunch$' -count=1 -v -timeout=20m
unset EVE_CONVEX_TOKEN
```

If the two M0 settings are in the ignored backend `.env.local`, explicitly load them for the **test harness** (Go does not autoload dotenv):

```sh
bun --env-file=./testdata/native-launch/packages/backend/.env.local -e 'const p = Bun.spawn(["go", "test", "./tests/m0", "-run", "^TestLiveConvexAndNativeLaunch$", "-count=1", "-v", "-timeout=20m"], {env: {...process.env, EVE_M0_LIVE:"1"}, stdout:"inherit", stderr:"inherit"}); process.exit(await p.exited);'
```

This bootstrap is not an application launch wrapper. The test excludes source `.env.local` files from its fixture snapshots and supplies only deployment-scoped keys to its temporary backend files. A production management credential belongs outside application configuration; do not treat this test setup as the eventual `eve auth` storage design.

The live probe validates token/team/project identity and original default deployment IDs before writes. It persists each random reference and finite expiry before a single management API create; verifies the returned cloud/dev/nondefault identity; creates a named deployment key; verifies listed key identity/expiry; obtains canonical URLs using the deployment API; and checks the copied public default marker. Only `SITE_URL` is written remotely. Deployment keys, never the management token, enter owner-only native backend files.

After binding, the ordinary unmodified launch command must push `probe:connection`. An unauthenticated query against the **intended deployment URL** must return the correct per-worktree `SITE_URL`; file contents or a CLI banner alone do not prove selection. Development-default inheritance is a separate mandatory subtest against the deployment API. The test also checks that A's key cannot read B's environment, deletes A, verifies B still works, then finalizes remaining resources and checks original project/default identities. No provider CLI is called during provisioning; `convex dev` runs only afterward as the application's existing backend command.

### Failed/interrupted live probe

- Subprocess output and raw provider response/error bodies are withheld because they may contain secrets. Safe HTTP status, phase evidence, and the evidence directory are available; no environment dump is emitted.
- The test prints an owner-only `/tmp/eve-m0-cloud-*` directory (the actual OS temp root may differ). Its synced JSONL files contain non-secret intent/observed identity; `.key` files, if present, are `0600`. Never publish `.key` files or native backend env files as CI artifacts.
- Finalizers re-read exact reference/name/ID/project/type/default/expiry before deleting only an owned deployment. A missing reference alone does not prove a known deployment is gone. Authentication/server failures are never absence. Unknown creation plus 404 stays unconfirmed; no new creation attempt is made for that intent.
- Successful cleanup removes protected key files. Failed assertions retain non-secret evidence; unresolved cleanup retains evidence/keys. Temporary Git checkouts are test fixtures and are removed by Go's test cleanup even if cloud cleanup fails. This is **not** the product's preserve-worktree failure policy or a production recovery implementation.
- Go finalizers do not run after SIGKILL, process crash, or test-runner timeout. Preserve the printed evidence directory, manually verify exact provider identities, and clean up only those test-owned deployments. Never delete the parent project/default deployment or select resources by an `eve` prefix. Five-day provider expiry is the fallback. There is no automated resume tool yet.
- Key-response-loss repair/rotation, provider-driven disappearance after waiting for TTL, and exhaustive fault recovery remain later gates; setting/reading a finite expiry is not evidence of elapsed-time deletion.
