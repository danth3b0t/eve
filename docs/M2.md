# M2 — Convex cloud integration

**Status: production cloud create/status/destroy works on Linux in the default region and `aws-eu-west-1`.** The guarded CLI provisions finite nondefault cloud development deployments, binds them through unchanged Bun/Turbo/Vite/Convex CLI scripts, uploads only declared backend environment values, and deletes those exact deployments during destruction. Linux browser validation with fixture configuration and a real headless browser passes; macOS, arm64 runtime and TTL-elapsed evidence remain pending.

## Implemented

- `eve auth convex login --project team:slug [--token-stdin] [--profile name]` validates lower-case project identity. Interactive terminals use a hidden token prompt; bare non-TTY input fails. `--token-stdin` is the explicit automation path and never stores shell variables in worktrees. Tokens are owner-only `0600` objects, not SQL and not encrypted. Existing profile team mismatch or secret change requires recovery, never silent rotation.
- The adapter uses only pinned Management/Deployment HTTP endpoints: fixed management origin, bearer team tokens, safe `*.convex.cloud`/`*.convex.site` deployment origins, 2 MiB bounded responses, redacted errors, no redirects, and no retry of non-idempotent writes. Convex CLI is not called for provisioning.
- Creation first commits deterministic workspace/resource references and intended TTL. It validates `teamToken`, project identity, and current default dev/production identities before mutation. Unknown deployment-create results remain `unknown`; exact-reference lookup reconciles them without choosing another name/reference.
- Nondefault cloud dev deployments require the response's exact project, reference, name/ID, type, default bit, safe URL, finite expiry, and creation window. Five-day default requests preserve the configured TTL; no clamping/extension fallback exists.
- Deploy-key intent precedes first use. A lost key response is repaired by revoking the exact previous key generation before creating another. Deployment key objects are protected and removed after destruction; no token or key appears in SQL, JSON/debug output, tracked files or deployment API bodies.
- Canonical URLs are read from the verified deployment. Only explicit `resources.<id>.env` mappings are uploaded; unrelated remote/default values are not copied, redistributed or logged. Source `CONVEX_*` selectors are never copied as-is.
- Native destinations receive only `CONVEX_DEPLOYMENT` and `CONVEX_DEPLOY_KEY` plus declared public resource outputs. They are journaled as protected private images, written to ignored files, and never appear in SQL JSON metadata or CLI output.
- Workspace status exposes only public resource identity/URL/expiry. Destroy checks local work/drift and ordinary process listeners first, deletes remote resources in reverse order, refuses project/default/identity mismatches, then removes the owned worktree, releases claims and purges deploy credentials. Remote deletion failures preserve the local worktree and its recovery record.
- A lost remote deletion response reconciles only after proving absence or exact identity. Protected SQL/metadata identities alone never authorize arbitrary prefix-based deletion.

## Runtime boundaries

EVE does not install packages, start applications, push project code, seed data, update development defaults, or keep apps alive after exit. The live fixture starts its ordinary unmodified Bun/Turbo commands once; Convex CLI—not EVE—pushed the fixture's committed schema. `code_status` remains `not_verified_by_eve`, and empty provider-initial data is not a login/account readiness claim.

HTTP/same-process access is not file encryption. Management credentials remain process-only overrides or protected profile objects. Current user/root can still read the owned store. Stopping an application can leave a claimed endpoint unavailable for roughly the host TCP post-close window; the native harness now closes client connections and waits up to 75 seconds before treating the lifecycle as stopped. EVE never identifies a process from a non-bind result or kills it.

## Evidence

- Offline contract tests cover exact project/default validation, regional origins, JSON wire agreements, key names/metadata, unsafe/malformed responses, no-write-retry, exact identity deletion and sanitized failures.
- Real Git/state/file lifecycle tests inject a contract-fake Convex transport and prove exact bindings, protected staging/publication, remote env selection, public frontend outputs, and local/remote destruction with secret purge.
- An ambiguous deployment-create response is reconciled from the exact recorded reference; only one POST happens in the test.
- A successful Linux dialogue with the real Convex API and production CLI created two workspaces in **80.74 seconds**. Both started unchanged `bun run dev` graphs, frontend listeners showed their own cloud/site URLs, and the actual backend reported the allocated `SITE_URL`. Stopping and destroying A left B functional; destroying B preserved its branches and the original project/default identities. The final list confirmed no `dev/eve/` deployment remained.
- Two earlier live runs revealed that immediate/5-second destroy checks can incorrectly treat post-close TCP unavailability as proof of a process and left **four deployments** pending. Each was independently verified as the test-owned, nondefault dev resource by exact reference/name/ID and deleted: `courteous-narwhal-266`, `adept-caterpillar-729`, `flexible-mongoose-553`, and `courteous-spaniel-409`. Deployment deletion used exact names, never prefixes or the parent project endpoint.
- A separate 96.91-second production-CLI run with `EVE_M0_REGION=aws-eu-west-1` created two regional workspaces, proved frontend URLs and backend `SITE_URL`, destroyed both, and left zero `dev/eve/` deployments.
- Linux race/native/CGo-disabled tests pass. All four `eve` binaries build CGo-disabled for Linux/macOS × amd64/arm64; only Linux/amd64 was executed.

## Not implemented

TTL-elapsed remote disappearance, exhaustive key-loss/out-of-band-revocation recovery, broader topology synchronization/remote reconciliation, broader provider cleanup previews, named profile deletion/rotation, package discovery, and elapsed-macOS/arm64 validation are still open. No periodic cloud cleanup exists; provider expiry remains the fallback.
