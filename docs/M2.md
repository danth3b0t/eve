# M2 — Convex cloud integration

**Status: authentication and provider-contract foundation only.** `eve auth convex login` validates an explicit lower-case `team:project` binding with a development team token and records the token outside the repository. Resource provisioning, key adoption/repair, remote env publication, integrated cloud destruction and status refresh are **not wired into create yet**.

## Implemented

- `internal/provider/convex` uses only pinned Management/Deployment HTTP endpoints. It validates lower-case `team:project`, `teamToken` type/team ID and an existing default cloud dev deployment before use.
- Deployment creation/inspection types require verified cloud/nondefault dev identity, exact reference/project/type/default/URL/expiry/creation window, and owned deploy-key format/metadata. Canonical HTTP Actions origins must be verified `*.convex.site` URLs.
- Credential-bearing requests never follow redirects, include raw response text in errors, retry a non-idempotent write, or call Convex CLI tooling. Response bodies are limited to 2 MiB; transport/server write outcomes are classified as ambiguous.
- `StoreManagementProfile` records immutable token-scope metadata and a high-entropy checksum before the owner-only `0600` token object is written. Complete missing-object recovery and interrupted logout/login reconciliation are supported. Partial or changed token objects are refused, never rotated. SQL contains no token.
- `eve auth convex login --project team:slug --token-stdin [--profile name]` stores one profile after provider validation. Profile scope records immutable team identity returned by that validation; later resource manifests must still name and reverify their exact project. Existing profile team mismatch is a conflict; profile token rotation is not implemented.
- `state.OpenReadOnly` still cannot read credentials. The token is protected by filesystem permissions only, not encryption; root/current-user access remains outside that claim.

## Test evidence

Offline provider tests cover exact creation request JSON, management/deployment authorization schemes, regional cloud/site origins, default workspace/name/type/default/bindings, canonical host/origin surprising strings, and wrong project/type/default/reference/expiry/name/ID cleanup refusal. Failed redirects, transports, credential-bearing bodies, server responses, malformed responses and oversize bodies are sanitized and no write is retried.

State tests cover concurrent registry constraints, private credentials, interrupted write intent, same-profile login reconciliation after a *complete missing* object only, partial/changed credential refusal, and cancelled stdin/profile operations.

## Not implemented

Durable resource creation, deploy-key persistence, referenced-name uniqueness, deployment environment defaults and declared remote env writes, all native `CONVEX_DEPLOYMENT`/`CONVEX_DEPLOY_KEY` images, remote cleanup and workspace-generated provisioning are still pending. Named profile deletion and hidden interactive input are also not implemented.

Until that is wired, do not point a resource-containing manifest at `eve create`: core continues to refuse publication with the existing provider-binding diagnostic rather than inventing a safe binding.
